# Connection lifecycle

## Lifecycle

1. Open a TLS WebSocket connection.
2. Authenticate when the connection is established.
3. Send one or more subscription frames.
4. Wait for an acknowledgement for each subscription.
5. Process messages and persist the latest checkpoint for each subscription.
6. If the connection closes, reconnect with exponential backoff and jitter.
7. Resume each subscription from its last persisted checkpoint. If that checkpoint is no longer valid, resynchronize from a snapshot.

## Heartbeats

The connection uses WebSocket ping and pong frames. Clients must respond promptly and should treat a missed pong as a dead connection, then reconnect. The ping interval and idle timeout will be published with the service.

## Checkpoints and gap detection

Every message carries a checkpoint. Clients persist the latest checkpoint for each subscription. A replay response indicates whether a gap occurred, so clients can determine when local state is untrustworthy.

## Resuming

Supply the last persisted checkpoint in the subscription object of the subscribe frame. Resume is per subscription rather than per connection because one connection can carry subscriptions at different positions. `cursor` is an accepted alias for `checkpoint` both when it is received in a message and when it is supplied for resumption. The checkpoint is opaque: clients store and return it unmodified, and its format may change.

## When to resynchronize

If a checkpoint is expired or rejected, or a gap is reported, discard local state and rebuild from a fresh snapshot before trusting it. This is especially important for book streams.

## Backpressure and slow consumers

Clients should apply bounded queues. A consumer that cannot keep up may receive an error frame before the connection is disconnected. The applicable thresholds will be published with the service.

## Errors

Errors arrive as a structured frame on the same connection. The error-frame shape and error codes will be published with the service.
