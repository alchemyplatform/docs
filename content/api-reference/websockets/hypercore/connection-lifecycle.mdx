# Connection lifecycle

1. Open a TLS WebSocket connection to the [endpoint](/docs/chains/websockets/hypercore) with your API key in the path. Requests without a valid key are rejected during the handshake.
2. Wait for `{"channel":"connected"}`.
3. Send one or more subscribe requests, each with its own `subscriptionId`.
4. Wait for each acknowledgement (`subscriptionResponse`) or error.
5. Process messages, tracking `seq` per subscription.
6. When the connection closes, reconnect with exponential backoff and jitter, then resubscribe. See [replay and recovery](/docs/chains/websockets/hypercore/replay-and-recovery).

Treat disconnects as routine. Deployments, maintenance, network interruptions, and slow consumers all close connections, and a closed connection is never resumed: you open a new one and subscribe again.

## Heartbeats

There is no heartbeat yet. A connection that receives no messages for about 90 seconds may be closed, which affects subscriptions that are often quiet, such as `userFills` for a few wallets. Reconnect when that happens, or keep a low-volume subscription (for example `bbo` for one active market) open on the same connection so messages keep flowing.

<Callout intent="info">
  A heartbeat is planned. Until then, `{"method":"ping"}` returns an `invalid_params` error.
</Callout>

## Sequence numbers

Every data and gap message carries `seq`, a counter scoped to its subscription:

* It starts at `1` for each new subscription, including after a reconnect.
* It increases by exactly one per message on that subscription.
* Acknowledgements and errors don't carry `seq`.

If `seq` skips (for example from `41` to `43`), you missed a message. On a book stream, your local book can no longer be trusted: resubscribe to get a fresh snapshot. On a fill stream, resubscribe with [`fromBlock`](/docs/chains/websockets/hypercore/replay-and-recovery) to recover the missing range.

<Callout intent="warning">
  Don't use `blockNumber` to detect missed messages on book streams. Book streams send a market only when it changes, so block numbers skip normally between messages.
</Callout>

## Slow consumers

The server buffers messages for each connection. If your client reads more slowly than data arrives and the buffer fills, the server closes the connection. The close code is `1008` with a reason when the close frame can be delivered; because the backlog sits ahead of it, many clients will instead see an abnormal closure (`1006`).

To avoid this:

* Read from the socket continuously and hand messages to a bounded queue for processing.
* Subscribe only to the markets and streams you need. Unfiltered book streams can be very large.
* Size receive buffers for large messages. A snapshot of every market's order-level book can be tens of megabytes; plan for messages up to around 100 MB if you subscribe to unfiltered `l4BookUpdates`.

## Close codes

| Code | Meaning | What to do |
| --- | --- | --- |
| `1000` | Normal closure | Reconnect if you still need data. |
| `1001` | Going away: the server is restarting or being deployed | Reconnect with backoff. |
| `1006` | Abnormal closure, no close frame (network interruption, idle timeout, restart, or a slow consumer whose close frame couldn't be delivered) | Reconnect with backoff. |
| `1008` | Policy violation, for example a slow consumer | Reconnect, then reduce volume or read faster. |

Restarts currently close connections without a close frame (`1006`); a graceful `1001` close is planned. Other codes may be added. Treat any unexpected close as a signal to reconnect with backoff.
