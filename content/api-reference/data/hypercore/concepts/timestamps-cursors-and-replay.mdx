# Timestamps, sequence, and replay

## Block number and block time

Every data message includes the source block:

* `data.blockNumber`: the HyperCore block height.
* `data.blockTime`: the block's time in Unix milliseconds.

Fill objects also carry their own `time` field, in Unix milliseconds.

HyperCore produces blocks every fraction of a second. Event streams (fills) send a message for each block that contains matching fills. Book streams send a market only when it changes, so block numbers skip normally between messages on book streams.

## Sequence numbers

`seq` is a counter on each subscription. It starts at `1` and increases by exactly one for every data or gap message on that subscription. A skipped value means a message was missed. Use `seq`, not block numbers, to detect missed messages. See [connection lifecycle](/docs/chains/websockets/hypercore/connection-lifecycle#sequence-numbers).

`seq` resets when you subscribe again, so it identifies position within a subscription, not a position in the chain. To resume, use block numbers.

## Replay

Fill streams accept `fromBlock` to replay recent blocks after a reconnect; persist the last processed `blockNumber` and resubscribe from the next block. Book streams don't replay; their first message is always a fresh snapshot. Replay depth is limited (plan to reconnect within about 30 seconds), and older ranges return a `gap` message. See [replay and recovery](/docs/chains/websockets/hypercore/replay-and-recovery).

## Deduplicating

| Stream | Identity |
| --- | --- |
| Fill streams | `tid` plus user. Both sides of a trade share one `tid`. |
| Book streams | No deduplication needed: a snapshot replaces state, and diffs apply in `seq` order. |
